# Первый прогон Minimal RAG

Анализ файла `rag_evaluation.json`, 16 вопросов. Повторные API-запросы при анализе не выполнялись. Оценка сделана по сохранённым ответам и переданным чанкам, а не только по эталонам.

## Результат

- Технические ошибки: 0 из 16.
- Полные правильные ответы на вопросы с ответом в корпусе: 6 из 13 (46,2%).
- Частичные ответы: 3 из 13.
- Отказы на вопросы, ответ на которые есть в корпусе: 4 из 13.
- Корректные отказы на вопросы без ответа: 3 из 3.
- Полный успех по всему набору, считая правильный отказ успехом: 9 из 16 (56,3%). Это ручная оценка одного небольшого прогона, не универсальная оценка модели.

Для строгой бинарной correctness частичные ответы здесь считаются неуспехом: вопрос должен быть закрыт полностью. В rag09 обе проблемы разделены: отсутствие Future связано с неполным контекстом, а смешение create_task и TaskGroup — с генерацией и потерей контекста на границе чанка.

## Retrieval: документ найден, ответ не обязательно найден

Хотя бы один документ из relevant_document_ids попал в выдачу для 12 из 13 ответимых вопросов. Все перечисленные эталонные документы попали для 11 из 13. Эти числа не означают, что нужное доказательство попало в контекст.

Особенно наглядны rag02, rag03 и rag12: нужный документ присутствует, но чанк с ответом отсутствует. Поэтому качество на уровне document ID выглядит заметно лучше качества конечного ответа. Для rag07 нужны разные сведения из нескольких мест, и текущая выдача содержит лишь часть.

Строгий отказ модели при недостаточном найденном контексте может быть корректным поведением генератора, но остаётся ошибкой системы в целом, если ответ есть в корпусе.

## Цитаты и grounding

В распознанных одиночных ссылках не обнаружено идентификаторов, отсутствующих среди переданных источников. При дополнительном разборе групповых ссылок также не обнаружено непереданных идентификаторов.

Но invalid_citations=[] не означает, что обработка цитат полностью корректна. В rag01 модель пишет `[python_26_string_trimming:0, python_26_string_trimming:1]`. Регулярное выражение в rag.py ожидает ровно одну пару в скобках и пропускает этот блок целиком. В sources записан только чанк 0 из другой одиночной ссылки; чанк 1, фактически процитированный моделью, потерян.

Следует либо потребовать отдельные скобки для каждого источника, либо поддержать группы в парсере. Инструкция сама по себе не заменяет проверку формата.

Смысл цитат также требует ручной проверки. В rag09 фраза про структурированную конкурентность относится в исходном документе к TaskGroup. Чанк 6 начинается с продолжения этой мысли, и модель связывает её с create_task. Существование идентификатора не гарантирует правильной атрибуции утверждения.

## Следующие действия

1. Сохранить этот прогон как исходную точку перед повторными экспериментами: main.py перезаписывает файл результатов.
2. Исправить учёт групповых цитат.
3. Провести сравнение с baseline той же моделью и параметрами: пока в файле есть только RAG, поэтому улучшение относительно обычной LLM не измерено.
4. Изолировать генерацию от поиска: для нескольких неудачных вопросов вручную передать чанки с ответом и проверить, исчезает ли ошибка. Такой запуск пока не выполнялся.
5. После этого менять одну настройку retrieval за раз, например top_k=3 на top_k=5. Это гипотеза улучшения, а не гарантия. Для rag02/rag03/rag12 полезно сначала проверить позиции нужных чанков в ранжировании без новых LLM-запросов.
6. Для составных вопросов отдельно рассмотреть поиск по частям вопроса. Для обрывов контекста — соседние чанки или границы смысловых блоков. Это возможные следующие эксперименты, не обязательное усложнение текущего задания.

В последующих результатах стоит сохранять название модели, параметры chunking, top_k и режим поиска, чтобы сравнения были воспроизводимы.
